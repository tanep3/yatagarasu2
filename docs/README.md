# Yatagarasu 2 文書案内

Yatagarasu 2の文書は、結論だけを保存するためにあるのではありません。なぜその構造になったのかを、次の人間とAIが再び導き出せるようにするためにあります。

## このプロジェクトを生んだ流れ

```text
「オブジェクト指向はなぜ挫折するのか」
  世界と、その世界が変化できる法則を記述するという理論
        ↓
soukoban
  閉じた小世界で、理論を動く構造として示した生きたお手本
        ↓
Yatagarasu 1
  実機を動かし、必要な機能・遅延・失敗・不確実性を発見した実験機
        ↓
Yatagarasu 2
  発見した世界を、状態・事実・規則・遷移・外部作用として再記述する基盤
```

Yatagarasu 1は、実機で検証された機能要件の基準です。凍結したYatagarasu 2の引継ぎドラフトは、構造要件の基準です。どちらも捨てて作り直す素材ではなく、原則として受け継ぐ完成度の高い原典です。現在の正本文書は、この二つを矛盾と未決事項が見える形で統合しています。

## 読む順番

| 知りたいこと | 文書 | 役割 |
| --- | --- | --- |
| 何を作り、利用者に何がうれしいか | [プロダクト](product/README.md) | 体験と使命を伝える |

| 原典の何を採用・保留・不採用にしたか | [根拠監査台帳](requirements/source-audit.md) | 要件漏れと黙った変更を防ぐ |
| 何がまだ決まっていないか | [トレーサビリティと未決事項](requirements/traceability.md) | 要件・受入条件・論点を結ぶ |

法務・データ境界は[法務文書](legal/README.md)、開発時の作業規約は[Agent Workflow](development/agent-workflow.md)にあります。

## 文書の権威

矛盾する場合は、適用範囲を明記したAccepted ADR、正本要件、アーキテクチャ説明、プロダクト説明、基準資料の順に判断します。ただし、これは古い資料を都合よく捨てる規則ではありません。除外には、矛盾、後続資料による訂正、既知の欠陥、意図的な延期、範囲外のいずれかの理由が必要です。

[引継ぎ時点の基準資料](drafts/handover-baseline/README.md)は変更せず保存します。思想の原典とsoukobanは、正本要件そのものではなく、正本の構造を理解・再生成するための読み解きの基準です。
