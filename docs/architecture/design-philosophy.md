# 設計思想 — 世界と、その変化を記述する

この文書は、Yatagarasu 2の設計判断を次の人間とAIへ移植するための中核文書です。規則を暗記するのではなく、未知の機能に出会ったとき、なぜその規則が必要かを再び導き出せることを目的にします。

## 構造がシステムを説明する

大きなシステムを理解するとき、巨大なメイン処理を上から追わなければ何も分からないなら、設計知識は実行順の中へ埋まっています。

Yatagarasu 2が目指すのは、その反対です。

- いま、どんな状態が存在するか。
- 何が起きた事実なのか。
- どの規則が適用できるか。
- どんな状態変化が許されるか。
- 外の世界へ、どんな仕事を依頼するか。
- その結果について、何が確認できたか。

これらの型、所有者、関係を読めば、中央の実行順を追わなくてもシステムの意味を復元できる。ここでいう「構造が説明する」とは、そういう意味です。

手続きや条件分岐そのものを否定するのではありません。局所的な検証に`if`があるのは自然です。避けるのは、新しい知識がすべて一つの時間順の主手順へ蓄積し、そこを変更しなければ能力を増やせない構造です。

## 四つの成果物は、一つの思考の連鎖である

```text
理論
「オブジェクト指向はなぜ挫折するのか」
  世界の構造と、可能な変化の法則を記述する
        ↓
生きたお手本
soukoban
  閉じた小世界で、観測・規則・遷移・状態を実行可能にする
        ↓
実機による発見
Yatagarasu 1
  音声、視覚、身体、記憶、Skill、遅延、失敗、不確実性を発見する
        ↓
再抽象化
Yatagarasu 2
  発見した世界を、外部作用と不確実性を含む法則として記述する
```

これはプロジェクトの思い出話ではありません。Yatagarasu 2の構造がどこから導かれたかを示す説明原理です。

### 理論 — オブジェクトではなく、構造を記述する

ここで受け継ぐ本質は、「現実の名詞をクラスにする」ことではありません。世界、事実、許される変化、責務の境界を型と契約で記述することです。

振る舞いを型として抽象化し、組み合わせによって全体を作る。新しい振る舞いは中央の条件分岐へ書き足すのではなく、新しい型、規則、境界として加える。その結果、プログラムは処理手順であると同時に、対象世界を説明する言語になります。

### soukoban — 最小の閉世界によるfew-shot

soukobanは、単なるゲーム実装でも、設計パターンのサンプルでもありません。理論を動く形で示すための、小さく制御された世界です。

- `GameState`は、いまの世界を表す。
- `WorldQuery`は、世界を変えずに観測する。
- `Rule`は、状態を直接書き換えず、可能な変化を生成する。
- `Transition`は、現在の世界を次の世界へ変換する値である。
- `Engine`はゲームの知識を持たず、生成された変化を適用するだけである。

重要なのは「プレイヤーを動かす処理」を中心に置かないことです。ある事実と規則のもとで、世界がどう変わり得るかを記述します。歩行、箱押し、滑る床、ワープなどは、中央エンジンを賢くするのではなく、規則を追加することで増やせます。

### Yatagarasu 1 — 現実世界を測った実験機

閉じたゲーム世界だけでは、ロボットに必要なものは分かりません。Yatagarasu 1は実際のカメラ、マイク、スピーカー、AI、アプリをつなぎ、机上では見えない世界を発見しました。

SBERTによる高速な意味反射、モデル常駐による待ち時間の削減、ウェイクワードの誤検出、自己音声の回り込み、完了通知を返さない機器、取消不能な動作、外部能力の障害、記憶とSkillの拡張性。これらはすべてYatagarasu 2の機能要件と構造要件の根拠です。

Yatagarasu 1の価値は、最終的な制御構造を完成させたことではなく、記述すべき現実世界を発見したことにあります。

## 類推が破れる場所に、Yatagarasu 2の発明がある

soukobanの構造は、そのまま現実のロボットへ移せません。類推が成立する部分を残し、破れる部分へ新しい構造を加えます。

| 閉じたsoukoban世界 | 開いたロボット世界 | Yatagarasu 2で加えるもの |
| --- | --- | --- |
| 世界の全状態をプログラムが知る | 外界の状態は部分的にしか観測できない | 観測、推定、要求、結果不明の分離 |
| 遷移を適用すれば世界が変わる | 命令を送っても物理世界が変わったとは限らない | 外部作用（Effect）と結果Event |
| 一手の結果は確定する | 完了通知がなく、成否を断定できない | Observed / Assumed / DefinitelyNotApplied / OutcomeUnknown |
| 単純な前後関係で動ける | 複合動作、資源競合、取消、並行処理がある | Effect Graph、依存関係、資源要求、guard |
| 再起動してもゲーム世界だけを復元すればよい | 外部作用を二重実行すると危険 | snapshot、durable pending、journal、照合方針 |

したがって、Yatagarasu 2の基本法則は次のようになります。

```text
WorldState + Event
  -> pure Rule
  -> Decision(Transition, Effect Graph)
  -> committed WorldState'
```

Transitionは、Yatagarasu内部で確定できる状態変換です。Effectは、外界へ依頼したい仕事を表す不変の値です。Effectを作っただけでは、カメラは動いていません。Adapterが実行を試み、結果をEventとして返し、その事実を受けて初めて次の判断を行います。

## Skillは、AIとアプリが同じ世界へ触れる接続面である

Skillを単なる「AIへの作業指示書」として扱うと、Yatagarasuの拡張性を見失います。

Skillは、人が使うアプリ、そのデータ、その機能をAIへ開く接続面です。人がWeb画面から使う世界へAIも触れ、読み、考察し、許された変更を提案できる。複数のSkillをAIが横断すれば、個別アプリの表示を越えた統合判断が可能になります。

ただし、Skillは万能な実行主体ではありません。次の概念を混同しません。

| 概念 | 責務 |
| --- | --- |
| Skill | アプリ、データ、能力をAIへ公開する接続面 |
| Contributor | SBERT、規則、LLMなど、意味解決へ候補や提案を寄与するもの |
| Proposal | 外部AIなどが返す、まだ許可されていない提案 |
| Effect | 方針の承認後に作られる、外部作業の不変値 |
| Adapter | Effectや外部入力を具体製品・通信・入出力へ翻訳する境界 |

Skillが手順説明を含むことも、Proposalを返すこともあります。しかし、それらはSkillの一部であって、Skillそのものの定義ではありません。LLMやSkillから来た提案は、方針検証を通るまで命令でも実行でもありません。

## SBERTは、意味空間を使う反射神経である

SBERTは、単なる文字列分類器でも、必ずLLMの前に通る固定工程でもありません。

通常の意味ルーティングでは、SBERTが言葉の意味の近さから候補を高速に返します。確信度が灰色の帯域にある候補は、その動作に固有のキーワードや純粋な規則で絞り込みます。十分に決定できる操作はLLMへ送らず、解釈や統合が必要な場合だけLLMへ提案を求めます。

機能によって、規則だけ、SBERTだけ、SBERTと規則、LLM提案だけ、複数候補の合成を選べます。中央の巨大な正式Intent登録簿へ、すべての概念を集約しません。登録するのは、候補をどう受け止めるかという版付きの方針です。

## 設計するときの思考手順

新しい機能を加えるときは、処理順を書く前に次を問います。

1. **世界の事実は何か。** 要求、観測、推定、提案、結果を分ける。
2. **誰が状態を所有するか。** 一つの状態に所有者を一つだけ置く。
3. **どの規則が判断するか。** 入出力を明示した純粋な規則にする。
4. **内部で確定できる変化は何か。** 決定論的なTransitionにする。
5. **外界へ頼む仕事は何か。** 不変のEffectとして表す。
6. **因果関係と競合は何か。** Effect Graphの依存、guard、資源要求にする。
7. **どんな結果が戻るか。** 成功だけでなく、失敗、取消結果、結果不明をEventにする。
8. **利用者には何を見せるか。** Projectionと通知方針を、内部事実から分ける。

この順序で説明できない機能は、まだドメインが十分に理解されていない可能性があります。

## Few-shot例（実装仕様ではない）

### 悪い例 — 知識が中央の時間順へ埋まる

```text
if request == "look right":
  camera.move_right()
  sleep(1)
  image = camera.capture()
  answer = provider.ask(image)
  speaker.play(answer)
```

この形では、移動が失敗した場合、結果が分からない場合、撮影資源が競合した場合、途中で取り消された場合の知識が、すべて主手順へ増えていきます。

### 良い例 — 世界の変化と外部作用を分ける

```text
Event: InteractionAccepted
Rule: 意味候補と方針から「右へ移動して観測する」を決定
Transition: 依頼済みInteractionを記録
Effects: MoveCamera, CaptureImage, RequestInterpretation, PlaySpeech
Dependencies: MoveCamera -> CaptureImage -> RequestInterpretation -> PlaySpeech
Guards: 移動結果とArtifactRefの有効性
Resources: camera.ptz, camera.capture, conversation, audio.output
```

移動が失敗または結果不明なら、guardが撮影以降を止めます。Adapterは世界状態を書き換えず、結果Eventを返します。

### 不適用 — 小さな判断までGraphにしない

```text
Rule: 設定値が範囲外 -> InvalidRequestとして拒否
```

ここには外部作用も因果関係もありません。純粋な検証で十分です。抽象化は、正確性、速度、診断、復旧、交換可能性、使いやすさのどれかを改善するときだけ導入します。

## 将来の実行可能シナリオ

将来、思想を文章だけでなく実行可能なfew-shotとして保つ場合、各シナリオは少なくとも次を持ちます。

```text
Scenario ID
Initial snapshot
Inbound Command/Event
Expected Decisions / Effect Graph
Adapter result Events
Final snapshot / Projection
```

現時点では、このテスト基盤が存在するとは主張しません。実装された時点で、説明とテストを同じ契約へ接続します。
